Distributed Inference Research Lab

Splitting Large Language Models Across CPU Clusters

CPUwiser is an empirical hobby laboratory designed to split single open-weight LLMs across multiple CPU nodes (1 coordinator + N workers) to measure tokens-per-second, time-to-first-token (TTFT), network latency sensitivity, and distributed failure behaviors under real hardware constraints.

Core Objective

Empirical Scaling

Measure exact latency and throughput trade-offs of tensor parallelism vs. pipeline splitting across commodity x86 and Arm CPUs without GPU accelerators.

Pinned Models

Qwen3 Architecture

Qwen3 0.6B for fast iterations & Qwen3 1.7B for main runs. Supported by both llama.cpp RPC and distributed-llama.

Key Mechanism

Profile & Planner

Pure declarative YAML profile ingestion with deterministic constraint solving: assigns layer cuts, quantizations, and thread pinning automatically.

Problem Statement & Motivation

State-of-the-art open-source LLMs require substantial memory bandwidth and capacity that exceed what a single budget machine or developer laptop can provide. While GPU clusters are prohibitively expensive, developers often possess idle CPU compute across homelabs, developer laptops, and free-tier cloud instances.

The Reality Check: Many naive claims suggest combining 10 weak free machines creates a high-performance "AI supercomputer". In reality, distributed CPU inference is memory-bandwidth bound and latency-fragile. CPUwiser treats rigorous measurement and understanding of these architectural limitations as the primary success criterion.
Challenge Hypothesis / Pitfall CPUwiser Design Solution
Memory Bandwidth Bottleneck Token generation requires reading the entire model weight matrix per token. CPU RAM channels are narrow compared to HBM. Distribute weights across multiple nodes via Pipeline Splitting (layer-by-layer) or RPC tensor-splitting to utilize aggregate memory capacity.
Network Delay Penalty Tensor-parallel inference requires sync barriers at every transformer layer, making it unusable over high-latency links. Introduce Linux tc netem network emulation in simulation; systematically sweep round-trip times (0.1ms to 50ms) to chart degradation slope.
Heterogeneous Compute Mixing fast x86 cores with low-power Arm cores causes stragglers in lock-step execution. Automated planner models per-node core capabilities, assigning proportional layers or non-uniform tensor splits.

System Architecture Overview

CPUwiser decouples pure orchestration logic from host execution. Profiles define physical cluster capabilities; the planner produces optimal deployment configs; engine adapters interface with execution engines (llama.cpp RPC, distributed-llama); and the test runner executes benchmarks with controlled network emulation.

Project Guardrails & Non-Goals

No Public RPC Exposure

llama.cpp RPC servers do not authenticate requests and are prone to arbitrary buffer execution. All worker nodes must bind strictly to local Unix sockets, Docker internal bridges, or WireGuard private subnets.

Always Free Cloud Enforcement

Cloud operations remain permanently capped inside Oracle Always Free limits (4 Ampere A1 OCPU cores, 24 GB RAM max, 2 micro AMD instances). Never provision paid shapes.

No Hallucinated Benchmarks

All performance metrics require verified source tagging: [V] Verified, [S] Third-Party Spec, [E] Arithmetic Estimate, or [U] Unknown.
